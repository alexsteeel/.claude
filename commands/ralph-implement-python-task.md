### 🚨 КРИТИЧНО: Skipped tests = FAILED TASK

**Stop hook заблокирует завершение если обнаружит skipped тесты!**

**ЗАПРЕЩЁННЫЕ паттерны** (hook их детектирует):
```
❌ "7 tests skipped"
❌ "marked for follow-up debugging"
❌ "@pytest.mark.skip"
❌ "2 passed, 5 skipped"
```

**Что делать если тест падает:**
1. **ИСПРАВЬ тест** — потрать время на отладку
2. Если не можешь исправить → **hold + blocks**
3. НЕ помечай как skip

**`@pytest.mark.skip` разрешён ТОЛЬКО если:**
- Тест был skip ДО начала текущей задачи
- Тест требует внешней инфраструктуры (CI, staging)

**`@pytest.mark.skip` ЗАПРЕЩЁН для:**
- Новых тестов, которые не проходят
- "Сложных" тестов, которые не хочется отлаживать
- Тестов "для follow-up работы"

### Обработка блокировок

При ЛЮБОЙ ситуации, требующей человека — **закоммитить работу, записать в blocks и выйти**:

```bash
# 1. Сохранить текущую работу (если есть изменения)
git add -A
git commit -m "WIP: {project}#{number} - blocked: {краткое описание}"
```

```python
# 2. Записать блокировку в задачу (используй поле blocks!)
blocks_text = """
- [{YYYY-MM-DD HH:MM}] {Краткое описание проблемы}
  - Что пытался сделать: {описание действий}
  - Почему не получилось: {причина блокировки}
  - Что нужно от человека: {конкретный запрос}
  - Коммит с незавершённой работой: {commit_hash}
"""

update_task(
    project="<project>",
    number=<N>,
    status="hold",
    blocks=blocks_text  # ← поле blocks, НЕ body!
)
```

**⚠️ ВАЖНО**: Коммит перед hold обязателен — иначе незавершённая работа будет мешать следующим задачам в loop.

**После записи блокировки — ВЫЙТИ. Не пытаться продолжать.**


### Запуск (ЕДИНСТВЕННЫЙ правильный способ)

```bash
Bash(command="ralph review {project}#{number}")
```

Команда последовательно запускает 4 отдельные сессии:
1. `/ralph-review-code` — 5 агентов параллельно
2. `/ralph-review-simplify` — code-simplifier
3. `/ralph-review-security` — security review
4. Codex review — direct CLI (via `ralph review`)

### Обработка замечаний (ОБЯЗАТЕЛЬНО для КАЖДОГО пункта)

**⚠️ КАЖДОЕ замечание** из review (любого уровня: CRITICAL, HIGH, MEDIUM, LOW, INFO) **ДОЛЖНО** иметь явную отметку в поле `review` задачи:

```python

update_task(
    project="<project>",

    review=existing_review + "\n\n### [main-claude] Response\n" + response_text

```

**Формат отметки для каждого замечания:**

⚠️ **Смайлы ОБЯЗАТЕЛЬНЫ** — они позволяют быстро выделить результат в стене текста!

```markdown
### [main-claude] Response

#### Code Simplifier
1. **Дублирование get_test_db_connection()** (High)
   → ✅ [main-claude] Fixed: удалён, используется fixture из conftest.py

2. **Константы дублируются** (Medium)
   → 📋 [main-claude] Deferred to #42: вынос констант в общий модуль

3. **Упрощение f-string в SQL** (Medium)
   → ❌ [main-claude] Declined: константы модуля, не пользовательский ввод, безопасно

4. **Избыточные комментарии-разделители** (Low)
   → ❌ [main-claude] Declined: улучшают навигацию в длинном скрипте

#### Security Review
1. **SQL Injection через String Interpolation** (Low)
   → ❌ [main-claude] Declined: значения — модульные константы, скрипт только для test DB
```

**Варианты действий (всегда со смайлом в начале!):**
- ✅ `✅ [main-claude] Fixed: <что исправлено>` — внесены изменения в код
- 📋 `📋 [main-claude] Deferred to #N: <причина>` — создана отдельная задача
- ❌ `❌ [main-claude] Declined: <обоснование>` — замечание не применимо/некорректно

**⚠️ ЗАПРЕЩЕНО:**
- Игнорировать замечания без отметки
- Писать общие фразы типа "все рекомендации учтены"
- Обрабатывать только CRITICAL/HIGH, пропуская остальные

## Phase 9: Cleanup

**После линтеров** выполни очистку перед сдачей:

### Шаг 1: Проверь и удали ошибочно созданные файлы

Проверь `git status` на наличие мусорных файлов, созданных по ошибке:

```bash
git status --porcelain | grep "^??"
```

**Типичные признаки мусорных файлов:**
- Файлы с пробелами/спецсимволами в имени: `"Exit code: "`, `"some output"`
- Файлы с именами bash-команд: `echo`, `cat`, `grep`, `test`, `true`, `false`
- Файлы с цифрами или случайными именами: `1`, `123`, `output`
- Пустые файлы без расширения в неожиданных местах

**Примеры мусора (удалить):**
```bash
rm -f "Exit code: " echo cat grep test true false
rm -f 1 2 3 output result tmp temp
```

**НЕ являются мусором** (легитимные файлы без расширения):
- `README`, `LICENSE`, `Makefile`, `Dockerfile`, `Procfile`
- `.env.example`, `.gitignore`, `.dockerignore`
- Файлы в `.git/`, `node_modules/`, `venv/`

**Если нашёл мусорные файлы — удали их перед коммитом.**

### Шаг 2: Проверь и исправь разрешения изменённых файлов

Используй `git status` для получения списка изменённых файлов:

```bash
# Получи список изменённых/новых файлов
git status --porcelain | awk '{print $2}'

# Проверь разрешения для каждого типа файлов
# Python модули должны быть 644 (rw-rw-r--)
# Shell скрипты должны быть 755 (rwxrwxr-x)
```

Для исправления разрешений:
```bash
chmod 644 path/to/file.py
chmod 755 path/to/script.sh
```

**Стандартные разрешения:**
| Тип файла | Права | Описание |
|-----------|-------|----------|
| `*.py` | 644 | Python модули |
| `*.sh` | 755 | Shell скрипты (исполняемые) |
| `*.html`, `*.css`, `*.js` | 644 | Web assets |
| `*.sql`, `*.yml`, `*.json` | 644 | Конфигурация и данные |
| `*.md` | 644 | Документация |

### Шаг 3: Отметь cleanup как завершённый

**ОБЯЗАТЕЛЬНО** напиши в отчете в фазе 11 фразу **"cleanup completed"** — это маркер для workflow hook.

Это защита от крашей: если сессия упадёт после update_task но до confirmation,

1. ✅ Сначала confirmation phrase (подтверждает что ВСЁ готово)
2. ✅ Потом update_task с status=done

## Error Handling

### Критические ошибки → blocks + hold

Следующие ситуации требуют **записи в blocks и статуса hold**:

| Ситуация | Действие |
|----------|----------|
| Codex недоступен | blocks + hold → ВЫЙТИ |
| Code review не выполнен | blocks + hold → ВЫЙТИ |
| Security review не выполнен | blocks + hold → ВЫЙТИ |
| md-task-mcp недоступен | blocks + hold → ВЫЙТИ |
| Непонятные требования в плане | blocks + hold → ВЫЙТИ |
| Неразрешимый конфликт с кодом | blocks + hold → ВЫЙТИ |

**ЗАПРЕЩЕНО:**
- Заменять недоступный инструмент собственным анализом
- Записывать своё ревью вместо codex/code-review
- Продолжать workflow при критической ошибке
- Игнорировать ошибки "инструмент недоступен"
- Использовать AskUserQuestion
- Ждать ответа пользователя

### Некритические ошибки (продолжать автономно)

| Ситуация | Действие |
|----------|----------|
| Замечание от ревью спорное | Исправить по best practices |
| Тесты падают | Исправлять итеративно пока не пройдут |
| Документация неполная | Обновить и продолжить |
| Linter ошибки | Исправить и продолжить |

### Паттерн blocks + hold

```bash
# 1. Сохранить текущую работу
git add -A
git commit -m "WIP: {project}#{number} - blocked: {краткое описание}"
```

```python
# 2. Записать блокировку (используй поле blocks!)
blocks_text = """
- [{YYYY-MM-DD HH:MM}] {Краткое описание проблемы}
  - Что пытался сделать: {описание действий}
  - Почему не получилось: {причина блокировки}
  - Что нужно от человека: {конкретный запрос}
  - Коммит с незавершённой работой: {commit_hash}
"""

update_task(
    project="<project>",
    number=<N>,
    status="hold",
    blocks=blocks_text  # ← поле blocks, НЕ body!
)
```

**После записи блокировки — ВЫЙТИ. Не пытаться продолжать.**
